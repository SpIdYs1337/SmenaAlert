# Uppetit IT

Внутренняя панель для контроля кассовых смен iiko, базы знаний, IT-инвентаря и учёта сотрудников. Оповещения о сменах отправляются через SMTP. [Инструкция по запуску веб-панели](WEB.md).

## Прежний режим с Яндекс Мессенджером

Проект для контроля **кассовых смен iikoFront через iikoServer / iikoChain API**.
Бот сверяет открытие каждой настроенной точки с её графиком и сообщает об опозданиях в рабочий чат
Яндекс 360. В сообщении перечислены ответственные точки. Одного сотрудника можно закрепить
за несколькими точками, а за точкой — несколько сотрудников.

В комплекте код на Python без сторонних Python-зависимостей, Docker Compose, примеры настроек
и автоматические проверки. Для рабочего запуска нужны доступы iiko и Яндекс 360.

## Как работает триггер

1. Дата контроля — текущая календарная дата **Europe/Moscow**, независимо от часового пояса хостинга.
2. Для точки выбирается время открытия на этот день. `off` означает выходной.
3. Начиная с контрольного времени бот запрашивает кассовые смены и смотрит их `openDate`.
4. При отсутствии открытия за текущую московскую дату бот отправляет тревогу с ответственными.
5. При последующем открытии отправляется одно сообщение с фактическим временем и опозданием.

Если бот запустился в 09:10 и увидел смену с открытием в 09:04 при графике 09:00,
он также сообщит об опоздании. Открытая вчера и не закрытая смена не засчитывается за сегодня.
Смена, открытая сегодня вовремя и затем закрытая, подтверждает факт своевременного открытия.
Для проверки берётся первое открытие за московскую дату.

По вашему условию «раньше времени открытия» сравнение по умолчанию строгое:
для 09:00:00 подходит открытие до 09:00:00. Если открытие ровно в 09:00:00 нужно засчитывать
вовремя, установите `at_deadline_is_on_time = true`.

По умолчанию достаточно одной кассы выбранного предприятия/группы. Для обязательного открытия
нескольких касс задайте `cash_register_numbers = [1, 2]` и `require_all_registers = true`.
При `false` достаточно любой кассы из списка; пустой список учитывает все кассы в выбранном предприятии.

Пример тревоги:

```text
🚨 Опоздание с открытием
Точка: Арбат
Дата: 18.11.2026, МСК
Открытие по графику: 09:00
По данным iiko на 09:05:00 кассовая смена за сегодня не открыта.
С контрольного времени прошло: 5 мин.
Ответственные: Иван Иванов (ivan@example.org)
```

Публичный Bot API Яндекса описывает доставку в группу и личную доставку по логину. Нативные `@`-упоминания
в сообщении бота в документации `sendText` не описаны. В группе бот показывает имя и логин. Настройка
`notify_responsibles_privately = true` добавляет личную копию первой тревоги для каждого ответственного.
[Яндекс Bot API — отправка текста](https://yandex.ru/dev/messenger/doc/ru/api-requests/message-send-text).

## Что потребуется

- Бот и OAuth-токен из кабинета организации Яндекс 360 для бизнеса. В интерфейсе это **Телемост → Боты**.
  [Инструкция Яндекса](https://yandex.ru/support/yandex-360/business/admin/ru/telemost/bot-platform).
- Целевой групповой чат, участие бота в нём и логины сотрудников с правом менять график и назначения.
- HTTPS-адрес iikoServer / iikoChain вида `https://company.iiko.it/resto`.
- API-логин и пароль с доступом к кассовым сменам нужных предприятий.
- `department_id` предприятий, при необходимости `group_id`, график каждой точки.
- Постоянно работающий сервер с доступом к `botapi.messenger.yandex.net` и вашему iiko.

Все точки сети нужно перечислить в `config.toml`. Команда `--discover` помогает получить их ID.
Новая точка не добавляется автоматически: ей необходимо задать график и ответственных.
Для общей базы сети заполняйте `department_id` каждой точки, чтобы смены разных предприятий не смешивались.
Для одного самостоятельного iikoServer с одной точкой фильтр предприятия можно оставить пустым.

## Запуск через Docker Compose

Команды выполняются в каталоге проекта. Нужны Docker и Docker Compose v2.

```bash
cp config.example.toml config.toml
cp .env.example .env
chmod 600 .env
chmod 644 config.toml
docker compose build
```

### 1. Получить ID чата и логины администраторов

Впишите в `.env` настоящий `YANDEX_MESSENGER_BOT_TOKEN`. После добавления бота в группу
запустите режим настройки. Он связывается только с Яндекс Мессенджером.

```bash
docker compose run --rm monitor --setup
```

Отправьте `/whoami` в целевую группу. Бот ответит вашим логином и ID чата. Остановите режим
настройки через Ctrl+C. В `config.toml` заполните строку `chat_id` и список `admin_logins`.
Если оповещения нужно направлять в тред, задайте `thread_id` равным ID сообщения, под которым открыт тред.

Контейнер работает от отдельного пользователя. `config.toml` должен быть доступен ему для чтения
(в примере права `644`); пароли находятся в закрытом `.env`, который читает Docker Compose на хосте.

Бот читает команды через `getUpdates`. Для этого в настройках бота должен быть пустой адрес вебхука.
[Документация Яндекса по опросу обновлений](https://yandex.ru/dev/messenger/doc/ru/api-requests/update).

### 2. Подключить iiko и настроить все точки

В `.env` задайте `IIKO_MAIN_LOGIN` и `IIKO_MAIN_PASSWORD`, в `config.toml` — настоящий `base_url`.
Пароли с `$` или `#` заключайте в одинарные кавычки в `.env`, например `IIKO_MAIN_PASSWORD='literal$value#'`.
Настройка `timezone` описывает часовой пояс времени **без смещения** в ответе iiko;
расписание контроля при этом всегда остаётся московским.

```bash
docker compose run --rm monitor --discover main
```

Перенесите UUID нужных предприятий в `department_id`, при необходимости UUID группы в `group_id`.
Скопируйте блок `[[outlets]]` для каждой точки сети и задайте все семь дней графика.
Если предприятий несколько и у них отдельные серверы, добавьте разделы `servers.second`,
`servers.third` с отдельными переменными логина/пароля и укажите нужный `server` в точках.

### 3. Проверить данные и запустить

```bash
docker compose run --rm monitor --validate
docker compose run --rm monitor --probe
docker compose up -d
docker compose logs -f monitor
```

`--validate` проверяет структуру настроек без сетевых запросов. Пример настроек тоже проходит такую проверку:
это не подтверждение правильности ваших UUID и доступов.
`--probe` читает только iiko, показывает количество записей и результат расчёта.
Этот режим использует расписание из файла, без изменений, сделанных командами чата.

Перед общим запуском проверьте на одной реальной точке, что уже открытая смена видна в API сразу,
её время правильно преобразуется в МСК и фильтр предприятия возвращает нужную кассу.
Скорость появления данных зависит от обмена между iikoFront и выбранным сервером, особенно для iikoChain.
Если выбранный сервер видит смену лишь после её закрытия или с большой задержкой, он не подходит как
источник для своевременного утреннего сигнала: потребуется более оперативный источник данных iiko.

Диагностику `--probe` и `--discover` выполняйте при остановленном основном экземпляре,
чтобы не создавать лишнюю параллельную API-сессию:

```bash
docker compose stop monitor
docker compose run --rm monitor --probe
docker compose up -d
```

Не запускайте несколько экземпляров одного бота. Файловая блокировка защищает один и тот же SQLite-файл,
но отдельные базы разных экземпляров не могут согласовать уведомления.

## Команды в чате

Пусть код точки — `arbat`. Посмотреть коды можно через `/points`.

| Команда | Действие |
| --- | --- |
| `/whoami` | Ваш логин и ID чата |
| `/points` | Точки, график на сегодня, ответственные |
| `/status` | Результаты и время последних проверок |
| `/responsibles arbat` | Ответственные точки |
| `/assign arbat` ответом на сообщение сотрудника | Сохранить логин и отображаемое имя автора |
| `/assign arbat manager@example.org` | Назначить по логину |
| `/unassign arbat manager@example.org` | Удалить назначение по логину |
| `/schedule arbat all 09:00` | Время открытия каждый день |
| `/schedule arbat mon,tue,wed,thu,fri 08:30` | Время по выбранным дням недели |
| `/schedule arbat sun off` | Выходной в воскресенье |
| `/schedule arbat all reset` | Удалить недельные изменения из чата |
| `/exception arbat 2026-12-31 off` | Выходной на конкретную дату |
| `/exception arbat 2026-12-31 10:00` | Другое время на конкретную дату |
| `/exception arbat 2026-12-31 reset` | Удалить изменение этой даты из чата |
| `/check` | Обновить данные и отправить положенные по графику тревоги |
| `/help` | Справка |

Изменять назначения и график, запускать `/check` могут сотрудники из `admin_logins` в настроенной группе.
Для одной точки можно назначить до 15 ответственных. Логин берите из `/whoami` или назначайте сотрудника
ответом на его сообщение.

Личная копия доступна сотрудникам организации, чьи настройки позволяют боту писать им.
Индивидуальная отправка выполняется после записи групповой тревоги. Если Яндекс отклонит личное сообщение,
ошибка попадёт в журнал, а сообщение в группе будет доступно.

Порядок выбора расписания: исключение даты из чата → исключение даты из файла →
день недели из чата → день недели из файла. Изменения действуют сразу; отправленные уведомления
не удаляются и не обнуляются. `reset` убирает только изменение из чата, затем используется значение из файла.

## Уведомления и сбои

- По умолчанию одна первичная тревога на точку за московскую дату и одно сообщение о последующем открытии.
- `repeat_after_minutes = 10` включает повторы, пока открытие не обнаружено. `0` отключает повторы.
- `notification_delay_seconds` позволяет дождаться обмена с сервером перед тревогой. Например, `60` проверит
  нарушение с дополнительной минутой ожидания, но опоздание всё равно считается от исходного графика.
- `poll_interval_seconds = 30` задаёт период цикла. Фактическая задержка включает время API-запросов;
  на общем сервере запросы последовательные, между разными серверами допускается параллельная работа.
- После подтверждённого своевременного открытия или доставленного сообщения о позднем открытии
  точка перестаёт опрашиваться до следующей московской даты. `/check` позволяет проверить её повторно.
- Недоступность, отказ доступа и неподходящий формат ответа iiko означают **неизвестный статус**.
  Это не считается подтверждённым опозданием. Через `api_error_after_minutes` после первой ошибки
  бот отправляет отдельное техническое уведомление, при восстановлении — сообщение о восстановлении.
- Если после тревоги сервер передал время своевременного открытия, бот отправит уточнение.
- Групповые уведомления получают стабильный `payload_id` для повторных попыток через Bot API Яндекса.
  После подтверждения отправки запись в SQLite предотвращает повтор тревоги при перезапуске.
- Пропущенные прошедшие даты не проверяются задним числом: триггер относится к текущей дате.

SQLite содержит дневные результаты, расписание из чата, назначения и позицию чтения Мессенджера.
В Docker это постоянный volume `bot_data`; при обычном перезапуске данные сохраняются.
Для резервной копии остановите бота и сохраните весь каталог/volume данных.
При переходе со старой версии заполните новый раздел `[bot]` по `config.example.toml` и назначьте ответственных
по логинам Яндекса. Дневные результаты и расписание можно взять из прежней SQLite.

## Запуск без Docker и проверка проекта

Нужен Python 3.11+ на Linux с системной базой часовых поясов (`tzdata`). Проверялось на Python 3.12.

```bash
python3 -m unittest discover -s tests -v
python3 -m shiftbot --config config.example.toml --validate
python3 -m shiftbot --config config.example.toml --demo
```

После заполнения `.env` и `config.toml`:

```bash
python3 -m shiftbot --setup
python3 -m shiftbot --discover main
python3 -m shiftbot --probe
python3 -m shiftbot
```

Для постоянной работы без Docker настройте системный сервис с перезапуском при сбое.
`.env` загружается автоматически; внешние переменные окружения имеют приоритет.
Нужны синхронизированные системные часы. Секреты не следует включать в архивы и репозитории.

## API и границы проверки

При подключении бот вызывает `POST /resto/api/auth` с параметрами `login` и `pass` (SHA-1 пароля).
При `405` адаптер пробует `GET` для совместимости с прежними установками. Полученный `key` используется
повторно. При истечении сессии бот обновляет ключ, при штатном выходе вызывает `GET /resto/api/logout`.
[iikoServer API — авторизация](https://ru.iiko.help/article/api-documentations/avtorizatsiya/).

В обычном цикле используется `GET /resto/api/v2/cashshifts/list`. Для сервера в МСК пример запроса
за 18 ноября 2026 года выглядит так.

```http
GET /resto/api/v2/cashshifts/list?key=KEY&departmentId=UUID&openDateFrom=2026-11-18&openDateTo=2026-11-18&status=ANY
```

`departmentId` отбирает торговое предприятие, `groupId` добавляется при настройке секции.
Обе границы включительные и передаются в формате `YYYY-MM-DD`. Если часы сервера настроены
на другую зону, бот запрашивает даты сервера, покрывающие московский день, и сверяет каждое `openDate` в МСК.
`status=ANY` позволяет увидеть факт открытия, даже если смену успели закрыть.
[iikoServer API — кассовые смены v2](https://ru.iiko.help/article/api-documentations/kassovye-smeny-v2/).

iiko возвращает JSON-массив объектов смен. Из поля `openDate` бот получает дату и время открытия.
`cashRegNumber` считывается только для точки с `cash_register_numbers`. Пример минимальных данных,
которые используются для обычной проверки, и результат при отсутствии смен.

```json
[{"openDate": "2026-11-18T08:54:00.000"}]
```

```json
[]
```

API возвращает и другие поля. Для расчёта достаточно даты и времени из `openDate`. Признак своевременного
открытия рассчитывается из первой смены за сегодняшнюю дату. Некорректный ответ означает неизвестный статус.
Команда `--discover` отдельно читает справочники `/resto/api/corporation/departments` и
`/resto/api/corporation/groups` при настройке. [iikoServer API — корпорации](https://ru.iiko.help/article/api-documentations/korporatsii/).

Яндекс Мессенджер получает `POST /bot/v1/messages/sendText/` с `chat_id` и `text`, а команды бот читает
через `GET /bot/v1/messages/getUpdates/`. Запросы используют заголовок `Authorization: OAuth <токен>`.
[Яндекс Bot API](https://yandex.ru/dev/messenger/doc/ru/).

Запросы используют проверку TLS. В журнал не выводятся пароли, токены, URL авторизации или тела ошибок сервера.
Поскольку классический протокол iiko передаёт `pass`/`key` в параметрах запроса,
на вашем прокси и сервере iiko эти параметры тоже следует скрывать в журналах.
Завершение процесса штатным способом позволяет освободить API-сессию; ограничения лицензии определяются вашей установкой.

Проверки проекта используют вымышленные данные и локальный HTTP-имитатор.
Они покрывают московскую дату, границу времени, вчерашнюю смену, выходные, несколько касс,
фильтры запросов, ошибки API, ограничения частоты, адресатов и права команд,
сохранение состояния и полный сценарий уведомлений после перезапуска.
